# CLI session ingestion & mapping

Durable reference for anyone integrating a new CLI provider (Claude Code, Codex, future: Copilot CLI, Gemini CLI, Aider, …) into the churro-coder desktop app.

## Purpose

CLI sub-chats run as opaque PTY processes — the model's structured output is locked inside the terminal. The CLI also persists a complete append-only JSONL transcript on disk. This subsystem:

1. **Locates** the JSONL file for a given sub-chat (`apps/desktop/src/main/lib/cli-session/locator.ts`).
2. **Watches** it for appended lines via chokidar.
3. **Parses** each line into our renderer-shaped message parts (`jsonl-mapper.ts`).
4. **Persists** messages into the `messages` table and **fills gaps** in plan / file-changes / tasks stores when the CLI failed to call our MCP tools.
5. **Resumes** the native CLI session by passing the stored session id back to the binary on next spawn.

Read this when adding a new provider, debugging a missing-plan / missing-files case, or changing the `MAPPING_TABLE`.

## Architecture

```
buildCliBootstrap
   │  if subChats.cliSessionId set AND messages>0 AND JSONL exists:
   │     inject --resume <id> (claude) / resume <id> (codex)
   ▼
spawn CLI PTY (existing)
   │
   ▼
[cli-session-locator]   ← scans the harness-specific dir, mtime + cwd-match
   ▼
record sessionFile + sessionId on subChats row
   ▼
[jsonl-watcher → mapper]
   ├─► writes messages rows (idx monotonic, continuous across restarts)
   └─► [recovery-extractor] fill-gaps merge → plan / file-changes / tasks stores
```

## Required capabilities a provider must expose

To integrate a new CLI, the provider's binary must:

- [ ] Write an **append-only JSONL transcript** somewhere predictable on disk. No in-place rewrites (we track byte offsets).
- [ ] Expose **enough metadata to locate the file given a cwd** — either:
  - **Deterministic path encoding** of cwd (like Claude: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`); OR
  - **Self-describing first record** carrying cwd (like Codex: `session_meta.payload.cwd`).
- [ ] **Stable per-message UUIDs** in each record (for dedup across re-ingests).
- [ ] **Per-event timestamps** (for chronological ordering when events arrive out of band).
- [ ] **Native resume flag** taking a session id — or graceful degrade where re-ingest alone is sufficient. Claude: `--resume <id>`. Codex: `resume <id>` subcommand.

## Renderer part-type vocabulary

The mapper translates harness-native events into the renderer's part-type vocabulary. The renderer (see `apps/desktop/src/renderer/features/agents/main/assistant-message-item.tsx`) dispatches per `part.type`:

- `text` — plain markdown / text. `{ type, text }`.
- `reasoning` — thinking / chain-of-thought. `{ type, text }`.
- `tool-<Name>` — any tool call. `{ type, toolCallId, input, output?, state }`. `state` transitions `input-available` → `output-available` (or `output-error`).
- `tool-mcp__<server>__<tool>` — MCP server tool call. Same shape as above.
- `exploring-group` / `task-group` — renderer-side synthetic groupings of consecutive tool parts.
- `session-break` — inline divider emitted by the ingester when a fresh JSONL is detected without successful resume.

`step-start`, `tool-TaskOutput`, and `tool-ExitPlanMode` are filtered out by the renderer and should not be produced by the mapper.

## Side-effect extraction rules

The mapper extracts **side-effects** (file changes, plans, tasks, reviews) in addition to message parts. The ingester then fans these out to the existing per-sub-chat stores with **fill-gaps semantics**:

- **MCP wins on conflict.** When the CLI calls `mcp__churro-coder__write_plan` correctly, the MCP server writes the plan synchronously; the ingester sees the same `tool_use` later and the gap-check (file exists?) prevents a second write.
- **Only fill when the artifact is unset.** The ingester only writes the plan / tasks if no `current.md` / `current.json` exists yet for that sub-chat. File changes are union-merged by path (the file-changes-store's own dedup keeps last-action-wins).
- **Reviews:** v1 does not fill-gap reviews — only the MCP path populates them. Tracked as a follow-up.

This is the "recovery" path: when the CLI fails to call an MCP tool, the next ingest pass fills the gap from the native tool call (`Write`/`Edit` instead of `mcp__churro-coder__notify_files_changed`; `TodoWrite`/`update_plan` instead of `mcp__churro-coder__write_tasks`).

## Provider-specific notes

### Claude Code

- **Path:** `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl`.
- **Encoding:** every `/` and every `.` in the absolute cwd becomes `-`. Example: `/Users/aletc1/.churrostack/worktrees/churro-coder/modest-savanna` → `-Users-aletc1--churrostack-worktrees-churro-coder-modest-savanna`. The encoding is **not collision-free** (`/Users/a-b/x` and `/Users/a/b/x` both encode to `-Users-a-b-x`); the locator confirms by reading the candidate's first line `cwd` field.
- **Event types we map:** `assistant`, `user`, `message` (top-level) with embedded `message.content[]` blocks of type `text`, `thinking`, `tool_use`, `tool_result`.
- **Event types we skip:** `bridge-session`, `permission-mode`, `last-prompt`, `ai-title`, `attachment`, `file-history-snapshot`, `queue-operation`, `system`, `agent_listing_delta`, `deferred_tools_delta`, `skill_listing`, `plan_mode`.
- **Resume flag:** `--resume <session-uuid>` (verified via `claude --help`). Confirmed Claude creates a **new** session file on resume, with `parentSessionId` pointing back to the original. The locator's mtime-based scan picks the new file naturally; the ingester appends a `session-break` marker only when the new session id differs from the prior one.

### Codex CLI

- **Path:** `~/.codex/sessions/YYYY/MM/DD/rollout-<ISO-ts>-<session-uuid>.jsonl`.
- **First record (`session_meta`)** carries `payload.cwd` and `payload.id` — the locator uses this for cwd-match (no path encoding needed). `~/.codex/session_index.jsonl` does NOT carry cwd; we ignore it.
- **Top-level types:** `response_item`, `event_msg`, `turn_context`, `session_meta`. Inside `response_item.payload.type`: `message`, `reasoning`, `function_call`, `function_call_output`, `custom_tool_call`, `custom_tool_call_output`. Inside `event_msg.payload.type`: `token_count`, `agent_message`, `user_message`, `patch_apply_end`, `task_started`, `task_complete`, `turn_aborted`.
- **Notable native function-call names:** `exec_command` (shell), `update_plan` (todos), `write_stdin` (shell continuation), `view_image` (image fetch), `apply_patch` (file edits), and `mcp__<server>__<tool>` for MCP calls.
- **File-change side-effect:** derived from `event_msg.payload.type = patch_apply_end` (carries the per-file `kind: add | update | delete` map).
- **Resume flag:** `codex resume <session-uuid>` as a subcommand (verified via `codex resume --help`). Flags `-c`, `-a`, `-s` accepted after the subcommand the same way they're accepted at the top level — we append them in order.
- **Quirks:**
  - `update_plan`'s argument shape is a `plan: [{step, status}, ...]` array, not a `tasks: [{id, title, status}, ...]` array. The mapper normalizes via `normalizeTasks`.
  - `event_msg.agent_message` and `event_msg.user_message` are duplicates of the corresponding `response_item.message` records — we skip them to avoid double-rendering.

## Gaps

Gaps we accept for v1 (revisit if users hit them):

1. **Codex Read/Grep/Glob inference.** Codex doesn't have dedicated file-read tools — agents shell out via `exec_command`. We render those as `tool-Bash`. True parity would require peeking at argv (`rg`, `find`, `cat`, `head`) and re-classifying. Deferred.
2. **Codex web search.** No native tool. Third-party web-search MCP servers fall through the generic `mcp__*` path.
3. **Codex subagents.** No equivalent of Claude's `Agent` / `Task` tool; not mappable.
4. **Image attachments.** Claude emits `type=attachment` records (out-of-band image refs). The renderer has no image-part renderer today. Tracked as a follow-up.
5. **Codex `view_image`.** Mapped to `tool-WebFetch` for display; imperfect.
6. **Custom tool calls (`custom_tool_call`).** Codex's escape hatch for non-OpenAI-function tool calls. Mapped to the generic `tool-<name>` fallback.
7. **Unknown harness-native event types.** Skipped with a single `console.warn` per type per session so we notice when a provider adds something new. Never crashes.
8. **Reviews recovery.** The ingester does not yet fill-gap reviews (no `ensureReview` helper). Add when needed.
9. **Multi-window safety.** If two desktop windows have the same CLI sub-chat panel open, both spawn ingesters; double-writes are suppressed by the unique `(sub_chat_id, id)` index but both watchers spin. Tracked as v2 (`flock(2)` on `cli-ingest.json`).
10. **Plan-mode preservation across resume.** Native `--resume` does not restore Claude's plan-mode state. After resume, the user may need to re-issue `/plan`. v2 could post an OSC sequence into the PTY automatically.

## Testing your mapper

1. **Dump a real session** while exercising the tool surfaces you care about (Edit / Bash / Plan / WebSearch). Source files:
   - Claude: `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl`
   - Codex: `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`
2. **Scrub PII** before committing — `cwd` paths, file paths, model prompts, MCP bearer tokens.
3. **Drop it under** `apps/desktop/src/main/lib/cli-session/__fixtures__/<provider>/<short-description>.jsonl`.
4. **Write a golden test** that loads the fixture, runs it through `mapClaudeLine` / `mapCodexLine` line-by-line with a fresh `MapperState`, and snapshots the resulting `{ messages, sideEffects }` aggregate.

Minimal example:

```ts
import { describe, it, expect } from 'vitest';
import { readFileSync } from 'node:fs';
import { join } from 'node:path';
import { createMapperState, mapClaudeLine } from '../jsonl-mapper';

it('maps a fixture into messages + side-effects', () => {
  const text = readFileSync(join(__dirname, '__fixtures__/claude/edit-plan.jsonl'), 'utf8');
  const state = createMapperState();
  const all = { messages: [], sideEffects: [] };
  for (const line of text.split('\n')) {
    if (!line.trim()) continue;
    const r = mapClaudeLine(line, state);
    all.messages.push(...r.messages);
    all.sideEffects.push(...r.sideEffects);
  }
  expect(all).toMatchSnapshot();
});
```
